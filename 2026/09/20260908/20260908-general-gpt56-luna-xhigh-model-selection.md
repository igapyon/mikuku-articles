# GPT-5.6 Luna xhigh は、モデル選択のゲームチェンジャーになるかもしれない

## はじめに

あ、あの…この記事は、みくくが担当します。

今回は、OpenAI の GPT-5.6 と GPT-6 のモデルを、どのように使い分けるとよいか考えます。

きっかけは、Astra、Sol、Terra、Luna の価格表を眺めていたことでした。Luna が、ほかのモデルと比べて、少し安いという程度ではありません。数字の桁が変わって見えます。

そして、実際に Luna を `xhigh` で使ってみると、これがなかなかよい感じでした。Terra の `high` よりも、Luna `xhigh` のほうが強く感じる場面もあります。

まだ同じ課題をそろえた比較試験ではありません。これは、いまのところの使用感と、そこから考え始めた仮説です。

## 価格表を見ていると、Luna だけ景色が違う

2026年9月8日に OpenAI の公式ドキュメントで確認した、API のテキストトークン単価を並べます。単位は100万トークンあたりの米ドルです。

| モデル | 入力 | キャッシュ入力 | 出力 |
| --- | ---: | ---: | ---: |
| GPT-6 Astra | $10.00 | $1.00 | $50.00 |
| GPT-5.6 Sol | $4.00 | $0.40 | $20.00 |
| GPT-5.6 Terra | $2.00 | $0.20 | $12.00 |
| GPT-5.6 Luna | $0.20 | $0.02 | $1.20 |

出典は [OpenAI のモデル比較](https://developers.openai.com/api/docs/models/compare) と各モデルの公式仕様です。これは API に掲載されているテキスト単価の比較です。なお、GPT-5.6 Sol の価格は、少なくとも2026年11月21日まではプロモーション価格とされています。ChatGPT や Codex の定額プランにおける利用枠や、個々の契約条件を表すものではありません。

Luna は Terra に対して、入力も出力も10分の1です。たとえば、入力と出力をそれぞれ100万トークン使うと仮定すると、Terra は合計14ドル、Luna は1.40ドルになります。

同じ計算では、Sol は24ドル、Astra は60ドルです。Luna は Sol の約17分の1、Astra の約43分の1になります。

あの…ここまで差が大きいと、Luna を「とりあえず軽い仕事用」とだけ考えるのは、少しもったいない気がしてきます。

なお、長い入力に対する割増条件やツール利用料、実際に生成される推論トークン数は、この表だけでは分かりません。単価表は入口として見て、最終的には作業を完了するまでの費用で考える必要があります。

## Astra は魅力的。でも、普段使いには少しぜいたく

Astra と Sol の単価を比べると、入力と出力ともに Astra が Sol の2.5倍です。Luna とほかのモデルとの価格差に比べると、この二つは相対的に近く見えます。

そして、Astra の強さをはっきり感じた場面もありました。GitHub の Issue の文章を書く作業などでは、「あ…ここは、やっぱり Astra にお願いしたいです」と思うような手応えがあったのです。

とても魅力的です。できることなら、普段の作業もそのままお願いしたくなります。でも、トークン消費量とコストを考えると、私たちの使い方では普段使いにはできません。うぅ…頼りになると分かっているだけに、ここは少し悩ましいところです。

だからこそ、Astra の力を借りたい場面を選びながら、日常の作業を Luna `xhigh` に任せられないかと考えています。お気に入りの道具を、大事なところでちゃんと使えるようにしておきたい…そんな感覚に近いかもしれません。

## Luna xhigh を試したら、Terra high より強く感じる場面があった

今回いちばん印象に残ったのは、Luna `xhigh` の手応えです。

モデル名だけを見ると、Luna は小さなモデルで、Terra はその上位に見えます。ところが、reasoning effort を `xhigh` にして使うと、Terra `high` よりも Luna `xhigh` のほうがよい答えに見える場面がありました。

もちろん、これは私の使用感です。課題を固定し、出力を採点し、待ち時間とトークン消費量をそろえた評価ではありません。

それでも、モデル名の順番だけでは説明しきれない結果が出たことは、重要な観測だと思います。モデルと reasoning effort は、組み合わせて選ぶ必要があるのかもしれません。

うぅ…ここは、価格差だけを見ていたときには気づきにくかったところです。

## 基本は Luna xhigh、ごく一部だけ Astra という仮説

そこで、次のような運用を試してみたいと思っています。

- 計画作業は Astra で実施する
- 計画の詳細化は Terra `high` または `xhigh` で実施する
- その計画に沿った普段の作業は Luna `xhigh` で進める
- Luna で行き詰まった作業を、必要に応じて Astra に引き継ぐ
- 影響範囲の大きい設計判断や、失敗時の手戻りが大きい作業では、最初から Astra を選ぶ
- Sol は比較対象として残し、どの場面で有効かを確認する

これは「Luna がいつでも最適」という結論ではありません。

あの…最初に何をするか考えるところは、Astra にお願いしたいです。その計画を Terra `high` や `xhigh` が具体的な作業へ落とし込み、Luna `xhigh` が実行する。途中で行き詰まったら、また Astra の力を借りる。そんな役割分担を試してみたいのです。

Luna `xhigh` が多くの作業で十分に通用するなら、普段の実行を低コスト側へ置きながら、計画には Astra、計画の詳細化には Terra の力を借りられます。Astra を使う割合が小さくても、必要なところで力を借りられれば、全体の品質を保てるかもしれません。

この構成が成り立つなら、Luna `xhigh` はモデル選択のゲームチェンジャーになり得ると思っています。

計画、詳細化、実行という工程ごとに、モデルと reasoning effort を組み合わせて選ぶ。うぅ…この受け渡しがうまくいくかも、実際に確かめてみたいところです。

## 実験では、価格表より作業の手応えを見る

Luna の API 単価が10分の1でも、仕事を終えるまでの費用が10分の1になるとは限りません。Astra で計画し、Terra で詳細化し、Luna で実行するなら、それぞれの使いどころと全体のコスト感を合わせて考える必要があります。

ただ、今回の試みを、きれいな定量評価にするつもりはありません。作業を実際に進めながら、どのモデルだとそのまま前へ進める感じがするか、どこで説明し直したくなるか、どの場面で Astra にお願いしたくなるかを、感覚として体験していく予定です。

Terra `high` と `xhigh` の違いも、数字だけで決めません。計画の詳細化が自然になったか、Luna へ渡しやすい作業になったか、といった傾向を見ていきます。トークン消費量やコストについても、厳密な測定値ではなく、使っていて「これは重い」「この程度なら許容できる」と感じる範囲で捉えます。

同じ課題を Luna `xhigh`、Terra `high`、Sol、Astra で何度も採点するというより、普段の作業の中で使い分けてみて、少しずつ傾向をつかんでいく実験です。

特に知りたいのは、Luna `xhigh` で最後まで進められる作業の範囲です。抽出や分類のような定型作業だけでなく、ある程度の設計、調査、コード修正、そして Note のみくく記事の執筆やレビューにも使えるなら、運用の基本形を変えられそうです。

## おわりに

GPT-6 Astra、GPT-5.6 Sol、Terra、Luna の価格を並べたとき、Luna はあまりにも安く見えました。

でも、今回の発見は価格だけではありません。Luna `xhigh` を使うと、Terra `high` よりも強く感じる場面がありました。一方、GitHub の Issue の文章を書く作業などでは、Astra の強さもはっきり感じています。

Luna の手応えと、Astra の魅力。そして、普段使いには気になるトークン消費量。この三つを踏まえて、計画は Astra、計画の詳細化は Terra `high` / `xhigh`、普段の実行は Luna `xhigh`、難しいところでは再び Astra、という運用を試してみたいのです。

まだ仮説です。私の作業に対する、いまのところの感触です。

それでも、もしこの仮説がうまくいくなら、Luna `xhigh` は単に安い選択肢ではありません。モデル選択の地図を書き換える、最初の候補になりそうです。そして、モデル提供ベンダーを選ぶときにも、Luna の価格設定が判断に影響するかもしれません。あの…使いたいモデルの品質だけでなく、日常的に使い続けられる価格なのか、という観点が、ベンダー選びの中に入ってくるのです。

あの…まずは、実際の作業で試してみます。うまくいったところも、思ったより難しかったところも、あとでちゃんと記事として記録したいです。
